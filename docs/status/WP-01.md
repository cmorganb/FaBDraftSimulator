# WP-01: Set ingestion + fixture set

**Status:** DONE
**Date:** 2026-09-14

## What was built

- `scripts/ingest_set.py`: maps the *real* upstream
  `the-fab-cube/flesh-and-blood-cards` JSON schema (confirmed via its
  published card-schema/abbreviations docs, not guessed) into
  `fabdraft_core.contracts.{Card,SetSnapshot}`. Key mapping decisions:
  - `uid = slug(name) + "-" + pitch_color` (e.g. `fixture-swift-strike-red`),
    matching plan section 5.1's stated rule ("a unique card is name +
    pitch"; printings collapse) rather than the plan's own `uid` *example*
    (`"IAR166-red"`, which looks printing-specific) - the prose is treated
    as authoritative over the illustrative example.
  - `rarity` mapped through an explicit `RARITY_MAP`; any code not in the
    map raises `DataIncompleteError` rather than being dropped or guessed.
    `"B"` for Basic is present but flagged as *inferred, not confirmed* -
    see `docs/status/BLOCKED.md`.
  - `classes`/`talents` derived from `types` via `KNOWN_CLASSES`/
    `KNOWN_TALENTS` lookup tables (the upstream schema has no separate
    fields for these) - explicitly best-effort general FaB knowledge, not
    from a machine-readable source. A card with an unrecognized type token
    is not miscategorized: it's kept in `subtypes` and the card is marked
    `data_complete=False`.
  - `equipment_slot`/`hands`, `specialization` (regex over functional text)
    are similarly best-effort derivations, documented as such.
  - `cost`/`power`/`defense`/`life`/`intellect`: variable values ("X", "*")
    parse to `null` rather than being guessed at - a known, documented
    contract limitation (the contract only supports integers).
  - Cannot be run end-to-end against real IAR data yet: the upstream `IAR`
    set entry is still a placeholder (checked 2026-09-14: `"name": "??? Set
    20 ???"`, no card rows). Mapping logic is unit tested (15 tests) against
    a small **fictional** mock payload
    (`scripts/tests/fixtures/mock_upstream_cards*.json`) shaped like the
    real schema - zero real Legend Story Studios card text in the repo.
- `scripts/generate_fixture_set.py` + `data/fixtures/fixture_set.json`
  (set code `FIXTURE`, 289 cards - see "S3/S4 discrepancy" below), plus
  `data/config/fixture.{expected_counts,pack_config,format}.json`. 3 fixture
  heroes (Brute/Necromancer/Runeblade, all Shadow-talent, mirroring the real
  IAR heroes' shape per S10), each with a Basic-rarity weapon and arm
  equipment. 20 of the 40 Majestic cards are marked `draftable=false`
  (expansion slot, S13); Basic/Legendary/Marvel/Fabled are all
  `draftable=false` too (chase-slot rarities per plan section 5.4).
- `data/config/iar.expected_counts.json`: the official IAR rarity split
  (plan S4), used by `scripts/ingest_set.py`'s `load_expected_counts()` so a
  set can never be ingested without an explicit, human-sourced expectation
  to check against - no code path infers "what the counts should be."

## Interfaces exposed

- `scripts.ingest_set`: `map_card`, `cards_for_set`, `build_snapshot`,
  `load_expected_counts`, `classify_types`, `derive_specialization`,
  `derive_equipment`, `make_uid`, `parse_int`, `RARITY_MAP`,
  `KNOWN_CLASSES`, `KNOWN_TALENTS` - all pure and unit tested independent of
  the network-fetching `main()`.
- `scripts.generate_fixture_set.build_fixture_set() -> SetSnapshot` - usable
  directly by tests (WP-05+) without touching disk.
- `data/fixtures/fixture_set.json`, `data/config/fixture.pack_config.json`,
  `data/config/fixture.format.json` - the working data source for every
  downstream WP until real IAR data exists.

## Decisions taken / VERIFY items resolved or escalated

- **Escalated to `docs/status/BLOCKED.md`:** plan section 2.4 S3 (263 total)
  contradicts S4's own itemized breakdown (sums to 289). Both are marked
  `VERIFIED` in the plan, so this isn't a case of picking a `VERIFY`-tagged
  estimate - it's an internal inconsistency in already-"verified" facts.
  Resolved *for this codebase* by using the itemized S4 breakdown (289,
  internally self-consistent and what rarity-indexed pack generation will
  actually use) for both `iar.expected_counts.json` and the fixture set,
  with the discrepancy documented in three places (this file, BLOCKED.md,
  and a comment at the top of `generate_fixture_set.py`) rather than
  silently resolved.
- **Escalated to `docs/status/BLOCKED.md`:** the upstream Basic-rarity
  shortcode is inferred (`"B"`), not confirmed from a real data row.
- S9/S13 (14 draftable of 16, expansion majestics non-draftable) are baked
  into the fixture set's per-card `draftable` flag as a convenience default;
  WP-05's pack generator is still the authority and may recompute this
  per-instance from `pack_config` rather than trusting the static flag.

## Known limitations

- `ingest_set.py`'s `main()` (network fetch + CLI) is not unit tested (would
  require mocking `httpx`); only its pure mapping functions are. It also
  cannot be exercised against real data yet (see above).
- Variable cost/power values ("X", "*") are not representable in the `Card`
  contract yet - `cost`/`power` become `null`. If IAR has such cards, this
  needs a contract change before WP-02 can call ingestion "complete" for
  those cards.
- `classes`/`talents`/`equipment_slot`/`hands`/`specialization` derivation
  is heuristic. It's been reasonable-general-knowledge-checked, not
  spec-checked, and must be re-validated the moment real IAR card text is
  available.
