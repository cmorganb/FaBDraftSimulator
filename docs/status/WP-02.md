# WP-02: Set validation gate

**Status:** DONE
**Date:** 2026-09-14

## What was built

- `packages/core/fabdraft_core/cards/integrity.py` (pure, no I/O):
  - `recompute_counts(cards)` / `find_incomplete_card_uids(cards)` - derive
    the truth directly from the card list, never trusted from a snapshot's
    own self-reported fields.
  - `IntegrityReport` (frozen dataclass): `counts_match`, `mismatches`
    (`{key: (actual, expected)}` for every disagreeing key),
    `incomplete_card_uids`, `is_fully_valid`, `data_integrity`
    (`"complete"`/`"incomplete"`).
  - `check_snapshot(snapshot, expected_counts)` - takes the authoritative
    expected counts as a parameter; deliberately does **not** read
    `snapshot.expected_counts` as ground truth, since the whole point of a
    validation gate is to catch a snapshot that's wrong about its own
    counts (tested explicitly: `test_check_snapshot_never_trusts_the_snapshots_own_expected_counts`).
  - `enforce_gate(report, allow_incomplete=...)` - raises
    `DataIncompleteError` (with the specific mismatches/incomplete uids in
    the message) unless the report is fully valid or `allow_incomplete` is
    set.
- `scripts/validate_set.py`: CLI (`--in`, `--out`, `--allow-incomplete`,
  `--config-dir` for tests) wiring the above to
  `scripts.ingest_set.load_expected_counts` (reused, not duplicated) and to
  disk I/O. Exit 0 on success (prints `data_integrity` status), exit 1 with
  a `REFUSED: ...` message on `stderr` when the gate refuses. On success it
  rewrites the snapshot's `integrity` field with the freshly recomputed
  values (not just passing through whatever was already there) before
  writing `--out`.
- 16 new tests (9 pure-core, 7 CLI-level) plus an integration test that runs
  the real `scripts/validate_set.py` against the committed
  `data/fixtures/fixture_set.json` and its own
  `data/config/fixture.expected_counts.json` - confirms WP-01's output
  actually passes WP-02's gate. `packages/core` is now at 100% coverage.

## Interfaces exposed

- `fabdraft_core.cards.integrity.{recompute_counts, find_incomplete_card_uids,
  IntegrityReport, check_snapshot, enforce_gate}`
- `scripts.validate_set.{validate, main}` - `validate()` is importable
  directly for anything that wants the gate without going through argv/exit
  codes (e.g. a future API endpoint).

## Decisions taken

- Verified manually (not just via tests) that `uv run python
  scripts/validate_set.py --in ...` works as documented: the initial
  version imported `scripts.ingest_set` without `scripts/` being on
  `sys.path` when run directly (it only worked under pytest, where
  `pythonpath = ["."]` papers over it) - fixed with a small `sys.path`
  bootstrap in `validate_set.py`. Caught by actually running the CLI, not
  just the test suite; worth remembering for any future `scripts/*.py`
  that imports another `scripts.*` module.
- `check_snapshot` takes `expected_counts` as an explicit parameter rather
  than reading it itself, keeping `fabdraft_core` I/O-free and testable
  with fabricated expectations (including the "snapshot lies about its own
  counts" case above).

## Known limitations

- `scripts/validate_set.py` doesn't yet get called by anything else in the
  pipeline (WP-05+ can call `ingest_set`'s output straight through
  `validate_set.validate()` once a real ingestion run exists).
- No CLI test covers a malformed/non-JSON `--in` file; `SetSnapshot.model_validate`
  will raise a `pydantic.ValidationError` in that case, which is reasonable
  but currently untested and prints a raw traceback rather than a clean
  `REFUSED:` message.

## What the next WP needs to know

- WP-05 (pack generator) and WP-06 (legality) are now both unblocked -
  their only other dependency (WP-04) was already done.
- Any future ingestion path (a real IAR run, or another set) should pipe
  its output through `scripts.validate_set.validate()` before treating a
  `SetSnapshot` as usable, rather than trusting `ingest_set.py`'s own
  embedded `integrity` field.
