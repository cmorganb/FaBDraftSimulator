# WP-05: Pack generator

**Status:** DONE
**Date:** 2026-09-14

## What was built

- `packages/core/fabdraft_core/packs/generator.py` (pure, deterministic):
  - `index_by_rarity(cards)` - indexes **deck-legal cards only**
    (`is_deck_card`) by rarity; heroes/weapons/arm-equipment are never
    eligible to appear in a generated pack (plan section 6.1: "excluding
    heroes/tokens per format config"). Verified explicitly by
    `test_no_hero_weapon_or_equipment_ever_appears_in_a_pack`.
  - `generate_pack(cards, pack_config, rng) -> Pack` - plan section 6.1's
    pseudocode, slot by slot in physical pack order, `rng.weighted_choice`
    per rarity draw, `rng.choice` among candidates, raising
    `PackGenerationError` (never silently relaxing) on pool exhaustion, an
    unrecognized rarity key, or a final card count that doesn't match
    `pack_config.pack_size`.
  - `Pack`/`PackedCard` dataclasses: a drafted instance's `draftable` flag
    comes from **the slot it was drawn from**, not `Card.draftable`'s
    static default - a rainbow-foil pull of what's normally a
    non-draftable-slot card is still draftable in that pack position,
    matching plan section 6.1's `instance(card, ..., draftable=slot.draftable)`.
  - Handles the chase slot's pseudo-rarity-keys (`M_expansion`, `CF`) from
    plan section 5.4's example config.
- `data/config/iar.pack_config.json` - the official IAR slot structure
  (plan S5/S7/S9), independent of whether real card data exists yet (this
  is a documented product fact, not data-dependent).

## Amendment to WP-01/WP-03 (found while implementing this WP)

Building this WP surfaced a real gap: nothing in the `Card` contract could
tell a core-subset Majestic apart from an expansion-slot one, which is
exactly what plan **S13** ("expansion majestics never appear in draftable
slots") requires the pack generator to enforce. Also found that
`scripts/ingest_set.py`'s `map_card()` hardcoded `draftable=False` for
every card and never looked at it - even though the real upstream schema
*does* carry this signal (`printings[].expansion_slot`, confirmed via the
same schema docs used in WP-01).

Fixed by adding a required `Card.is_expansion_slot: bool` field
(`contracts/card.schema.json`, regenerated) and a
`default_draftable(rarity, is_expansion_slot)` helper in
`scripts/ingest_set.py`, now used by both real ingestion (mapped from
`printings[].expansion_slot`) and `scripts/generate_fixture_set.py` (which
already knew which 20 of its 40 Majestics were "expansion" - it just wasn't
recording that fact on the `Card` itself). All existing Card-constructing
tests were updated for the new required field;
`data/fixtures/fixture_set.json` was regenerated. See the amendment notes
in `docs/status/WP-01.md` and `docs/status/WP-03.md`.

## Decisions taken

- **S13 enforced structurally, not just by convention**: any slot with
  `draftable=True` automatically excludes expansion-slot Majestics from its
  candidate pool, regardless of whether `majestic_subset` is explicitly set
  to `"core"` - so a future config that adds a new draftable slot without
  remembering to set `majestic_subset` still can't violate S13.
  `majestic_subset: "expansion"` is honored explicitly for a non-draftable
  slot that wants only expansion Majestics (the `chase` slot uses the
  simpler `M_expansion` pseudo-key for this instead, but the explicit-field
  path is also supported and tested).
- Cold foil (`"CF"` pseudo-key) draws from the full deck-card pool
  regardless of rarity - this is a deliberate simplification of an already
  `confidence: ESTIMATED` slot, not a guess dressed up as fact.
- `generate_pack` takes `cards: list[Card]` rather than a full
  `SetSnapshot`, since only the card list is needed and this keeps the
  function trivially reusable/testable.

## Known limitations

- No real IAR card data exists yet, so `iar.pack_config.json` has never
  been run against real cards - only against `FIXTURE`.
- The rainbow-foil and rare-or-majestic slot weights remain
  `confidence: ESTIMATED` (plan S14/S15) - the statistical test checks the
  generator honors *whatever* weights are configured, not that those
  weights are correct.
