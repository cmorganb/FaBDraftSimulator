# WP-07: Draft state machine

**Status:** DONE
**Date:** 2026-09-14

## What was built

- `packages/core/fabdraft_core/draft/pod.py`: `pass_direction(round)` / `next_seat(seat, round, pod_size)`.
  `# TRP 8.2.1`: "the first pack to their left, the second pack to their
  right, and the third pack to their left" (verified verbatim against
  `docs/sources/en-fab-trp.txt`, not committed).
- `packages/core/fabdraft_core/draft/timers.py`: the `# TRP A.3` per-pick
  timer table and the 1-minute review window, verified verbatim against the
  real TRP text (my earlier plan-derived table matched exactly).
- `packages/core/fabdraft_core/draft/clock.py`: `SimClock` (never actually
  waits in real time - a pick source either answers or returns `None`, at
  zero real-time cost) and `RealClock` (`asyncio.wait_for`-based, for an
  eventual interactive session). This is what makes a full simulated draft
  run in milliseconds while still being able to drive a real, human-paced
  session later without changing the engine.
- `packages/core/fabdraft_core/draft/state.py`: `DraftState` (immutable,
  fold target) and `draft_reducer(state, event) -> DraftState` covering
  every draft-phase event type. Card *identity* (`CardRef`: uid + slot +
  foiling + draftable) is what state tracks - full `Card` data (name, text,
  rarity...) is static catalog data resolved separately, kept out of state/
  events entirely so both stay small and cheap to replay (WP-12).
- `packages/core/fabdraft_core/draft/engine.py`: `run_draft(...)` - the
  full plan section 6.2 loop (open packs, remove extras, 14 pick-and-pass
  cycles per round with shuffle-then-pass, review window, three rounds,
  finalize), producing an append-only `EventStore` and returning the final
  `DraftState`. `PickSource` is a deliberately minimal, temporary interface
  (see its docstring) - WP-08 (information policy) and WP-14 (agent
  protocol) don't exist yet, so the engine can't accept a real `Agent` +
  `AgentView`. A pick source only ever sees its own seat's current pack,
  which happens to already be a safe subset of the eventual AgentView.

## A real spec inconsistency found and resolved (not a `VERIFY` item - a proven contradiction)

Plan section 6.2 states as an invariant: **"A seat never receives the same
pack twice within a round."** This is mathematically impossible for an
8-seat pod running 14 picks per round, and directly contradicts the plan's
*own* glossary (section 17): **"Wheel: A pack returning to a seat after
passing around the pod (with 14 cards and 8 seats, picks 9 to 14 come from
wheeled packs)."**

Proof: with a fixed pass rotation, the pack that originated at seat O is
held by seat `(O + k) mod 8` after `k` passes. At pick `k+1`, a pack has
undergone exactly `k` passes, so at pick 9 (`k=8`), `(O + 8) mod 8 = O` -
the pack is back with its own originating seat. This is not an edge case;
it happens for picks 9-14 (6 of the 14 picks), for every seat, every round.

Implemented the **correct** behavior (matching the glossary and real TRP
8.2.1 procedure - shuffle-then-pass with no exception for wheeling) and
added `test_wheeling_matches_the_plan_glossary` to pin it, rather than
implementing a hard assertion that would reject valid, rules-accurate draft
behavior. See the "RESOLVED" entry added to `docs/status/BLOCKED.md`.

## Decisions taken

- **Event payloads record outcomes, not instructions to re-derive them.**
  E.g. `PACK_SHUFFLED`'s payload is the resulting card order (not "shuffle
  with this rng call"), and `PACK_PASSED`'s payload is "here is your new
  pack" computed from a single pre-pass snapshot (not an imperative "move"
  applied seat-by-seat, which would have cross-seat ordering hazards). This
  keeps `draft_reducer` a trivial, order-independent function of recorded
  facts - exactly what WP-12's replay needs.
- **A called draft's timer runs its full nominal duration in simulated
  time**, regardless of how fast a pick source actually answers (`SimClock`
  advances by `timer_seconds` after gathering picks) - this is what makes
  `test_round_duration_matches_plan_section_2_2` land on exactly 360,000ms
  while the real wall-clock run stays under 2 seconds.
- **`POOL_FINALIZED`'s payload is a single pod-wide total**, never a
  per-seat breakdown, so it can never be mistaken for exposing another
  seat's pool even in the raw event log.
- Only `timeout_policy: random` (plan section 3.3) is implemented;
  `heuristic_best` needs a real heuristic agent (WP-15) and isn't
  approximated here - `auto_pick` is a pluggable callable specifically so
  WP-15 can supply a better one without changing the engine.
- `picks_per_round` is derived from `pack_config` (`sum(slot.count for
  slot if slot.draftable)`), never hardcoded to 14, per the plan's own
  "must not hardcode IAR" principle.

## Known limitations

- `PickSource` is explicitly a placeholder. WP-08 will need to either wrap
  a real `Agent`+`AgentView` into this shape, or the engine's pick-gathering
  loop will need a small refactor to accept them directly - flagged, not
  silently worked around.
- Casual mode / memory policy (plan section 3.2/8.3) aren't implemented -
  out of scope for WP-07 (information policy is WP-08).
- No human/API latency simulation for `RealClock`-driven sessions yet -
  that's WP-14 (human adapter) / WP-18 (API transport) territory.

## What the next WP needs to know

- WP-08 (information policy) builds `core/draft/views.py` on top of this
  engine's `DraftState`/events - it needs to resolve `CardRef.uid` back to
  full `Card` data via a catalog (`{c.uid: c for c in cards}`, same pattern
  `engine.py` already uses) when constructing an `AgentView`.
- WP-11 (log writers) can iterate `EventStore.events` directly; every event
  type this WP emits is documented above with its exact payload shape (see
  `engine.py`'s event-building call sites).
- WP-12 (replay) should call `fold_draft_events(events)` and expect it to
  reproduce the exact same `DraftState` a live `run_draft` call would have
  produced at each point - this is enforced by construction (the engine
  itself folds every event it emits through the same `draft_reducer`).
