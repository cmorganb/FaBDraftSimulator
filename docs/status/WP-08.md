# WP-08: Information policy enforcement

**Status:** DONE
**Date:** 2026-09-14

## What was built

- `packages/core/fabdraft_core/draft/views.py`: `build_agent_view(events, state, seat, catalog, fmt, policy=...) -> AgentView`, the plan section 3.2 information-hiding rules implemented as a pure function over WP-07's `DraftState` + event log.
  - `ViewPolicy` (frozen dataclass): `memory_policy: "none"|"own_pool"|"full_recall"` (default `"own_pool"`, plan section 8.3) and `casual_mode: bool` (default `False`) - never loaded from anywhere by this module; the caller decides, matching `fabdraft_core.cards.legality.FormatRules`'s precedent for "policy passed in, not read from disk."
  - `FormatSummary`/`HeroSummary` (frozen dataclasses): just what `AgentView.format` needs (deck_size, hero uid/name/classes/talents, basics_available) - deliberately *not* the full `*.format.json` shape (basic weapon/equipment uids, banned lists), which is WP-09's concern to load and own. Keeps this module decoupled from WP-09's format-config work happening in parallel.
  - Current pack: always visible, resolved from `state.seat_packs[seat]` via the uid→Card `catalog` pattern already used throughout the codebase (WP-05/WP-07).
  - `own_pool`/`own_pool_visible`: only visible when `policy.casual_mode` is set - see "Scope decision" below for why the plan's "or in a review window" clause isn't reachable from this function.
  - `memory.own_picks_this_round` / `memory.seen_packs`: derived by filtering the **event log** (not `DraftState`, which doesn't track per-round pick boundaries) for `PICK_MADE`/`PICK_AUTO` and `PACK_OPENED`/`PACK_PASSED` events matching `seat` and the current `state.round`. `seen_packs` only populates under `memory_policy="full_recall"` (deliberately superhuman, plan section 8.3) and is normalized to draftable-only card counts (a raw `PACK_OPENED` payload still includes the 2 non-draftable extras at that point; filtered out here so every entry in `seen_packs` has a consistent, draftable-only shape).
  - `time_limit_ms` derived from `fabdraft_core.draft.timers.timer_seconds_for_pack_size(len(current pack))`; `pass_direction` from `fabdraft_core.draft.pod.pass_direction(state.round)`.

## Scope decision: active pick-window only

`AgentView`'s schema (`contracts/agent_view.schema.json`) requires `round >= 1` and `pick_number >= 1`. WP-07's `DraftState` resets `pick_number` to `0` at `ROUND_COMPLETE` and clears `seat_packs` between rounds, and there is no `DraftState.phase` value representing "between rounds, reviewing, about-to-start-next-round" that carries a schema-valid `round`/`pick_number` pair. Concretely: there is no way to build a schema-valid `AgentView` for the "review window" moment the plan's own information table describes ("own drafted pool during review window and after: visible") - it isn't a pick-window at all.

**Decision:** `build_agent_view` is scoped to exactly one thing - the per-pick view during an active pick window (`state.phase == "drafting"` and the seat holds a non-empty pack) - and raises `ValueError` for anything else (not started, between rounds, no pack). A `ReviewView` (named in plan section 8.1's `Agent.review(self, view: ReviewView)` but with no contract of its own in `contracts/`) is a distinct, not-yet-specified concept and is explicitly out of scope here. This is why the acceptance criterion "`own_pool` empty unless in a review window or `casual_mode`" is tested here only via the `casual_mode` half - the review-window half needs its own future view type once one is specified (flagging this rather than stretching `AgentView` to cover a state its schema can't represent).

## Decisions taken

- Views are built from **one real running draft's event log** in tests (via `run_draft` against `FIXTURE` data), not a hand-rolled `Hypothesis` strategy for arbitrary `DraftState` values. `DraftState` has internal consistency constraints (pack_id lineage, pack/pool complementarity) that are easy to violate with a naive generator but guaranteed to hold for anything the real engine produces - Hypothesis then fuzzes seat/policy/point-in-draft combinations against several real truncated-event-log snapshots (picks 1, 5, 9 of round 1; 1, 9 of round 2; 14 of round 3 - chosen to cover pre-wheel, post-wheel, and every round's pass direction).
- Defense-in-depth: after constructing and validating the view, the function re-asserts `view.seat == seat` and raises if that's ever false. This is structurally unreachable (everything above is built solely from `catalog`, which carries no seat identity, plus per-seat slices already filtered to `seat`) but is the concrete, testable form of "violation raises rather than filters silently" the acceptance criteria ask for - left uncovered by coverage deliberately, same precedent as `engine.py`'s own defensive branch (see its status doc).

## Known limitations

- No `ReviewView` - see "Scope decision" above. Whoever specifies one (likely alongside WP-21's deck-build/review screen work, or earlier if WP-11's log writer wants a "review notes" section) should reuse `own_pool`/`memory` visibility logic from here rather than re-deriving it.
- `Essence`-style meta-static abilities that would grant additional legal supertypes are not modeled (same gap already flagged in WP-06) - doesn't affect information policy, only legality, but is adjacent enough to note again here since `format.heroes` is the same kind of summary data.
- `FormatSummary`/`HeroSummary` here and whatever WP-09 defines for its own deck-building format needs are intentionally separate types (each consumed by different code paths); there was no coordination between this WP and WP-09 (built in parallel in a separate worktree) beyond both existing - do not assume they're interchangeable without checking.

## What the next WP needs to know

- WP-14 (agent protocol) should replace `fabdraft_core.draft.engine.PickSource` (the temporary "sees a raw `list[Card]`" seam WP-07 introduced) with something that calls `build_agent_view` and hands the resulting `AgentView` to a real `Agent.pick()`. The natural integration point is inside whatever wraps `PickSource.get_pick` for a real agent - `pack: list[Card]` there is exactly `state.seat_packs[seat]` resolved, i.e. exactly what this module already produces as `view.pack`.
- WP-11 (log writers) needing "what did seat X see when it picked" for the human-readable log can reuse `build_agent_view` directly rather than re-deriving pack/pool history from events.
