# WP-09: Deck build + validation

**Status:** DONE
**Date:** 2026-09-14

## What was built

- `packages/core/fabdraft_core/deck/builder.py` (pure, no I/O):
  - `legal_pool(drafted_cards, all_set_cards) -> list[Card]`: plan L1 - the
    drafted cards plus every Basic-rarity card in the set that wasn't
    already drafted. A young hero's own dedicated basic weapon/arm
    equipment (plan S10) needs **no special-casing**: it's already
    Basic-rarity, so it's already in this pool via the general rule, and
    `card_playable_by` (WP-06) is what naturally keeps e.g. a Necromancer's
    basic weapon illegal for a Brute hero even though it's freely
    available. Verified directly (`test_a_different_heros_basic_gear_is_available_but_illegal`).
  - `validate_deck(pool, hero, arena_cards, deck_cards, deck_size=30,
    format_rules=None) -> ValidationResult`: reaches every one of the 9
    violation codes from `contracts/decklist.schema.json`'s
    `Violation.code` enum, each backed by a real citation:
    - `NO_HERO` / `HERO_NOT_YOUNG`: no hero selected, or hero lacks
      `"Young"` in `subtypes` - confirmed against real ingested IAR data
      that every young hero has `"Young" in card.subtypes` (never in
      `types`), adult forms don't (see the WP-08/09-adjacent fix commit
      that moved the fixture set's own heroes to match this exactly).
    - `DECK_SIZE`: exactly `deck_size` (default 30, plan L5) deck-cards.
    - `ARENA_CARD_IN_DECK`: `# CR 1.3.2d / CR 4.1.5a` - "An arena-card...
      cannot start the game in a player's deck." Broadened to "must
      actually be `object_type == 'deck'`" so a hero or token card ending
      up in `deck_cards` by caller error is caught the same way, not just
      literal arena cards.
    - `NOT_IN_POOL`: card not in the computed `legal_pool`.
    - `ILLEGAL_CARD`: `card_playable_by` fails (class/talent/Specialization).
    - `EQUIP_SLOT_CONFLICT`: `# CR 4.1.4a` - "up to one arena-card for each
      of... arms, chest, head, legs" - more than one per body slot.
    - `WEAPON_HANDS`: `# CR 3.0.2` (two weapon zones total) / `# CR
      3.16.2a`, `8.2.1b`, `8.2.2b` ((1H) needs one zone, (2H) needs two) -
      sum of selected weapons' `hands` exceeds 2.
    - `FORMAT_RESTRICTION`: a banned-in-limited card (plan L7 / TRP 8.2),
      checked **independently of hero selection** - unlike `ILLEGAL_CARD`,
      which needs a hero to check class/talent against, a format-wide ban
      applies regardless (`test_format_restriction_fires_even_without_a_hero`).

## Interfaces exposed

- `fabdraft_core.deck.builder.{legal_pool, validate_deck, Violation,
  ValidationResult, ViolationCode, WEAPON_ZONES, DEFAULT_DECK_SIZE}`

## Decisions taken

- **`FORMAT_RESTRICTION` vs `ILLEGAL_CARD` split**: `card_playable_by`
  (WP-06) already has its own `banned_in_limited` check baked in. Rather
  than let a banned card produce a confusing `ILLEGAL_CARD` (which reads as
  "wrong class/talent"), `validate_deck` calls `card_playable_by(card,
  hero)` **without** `format_rules` (so its internal banned-check never
  fires) and instead checks `banned_in_limited` itself, reporting
  `FORMAT_RESTRICTION`. This also makes the ban check hero-independent,
  which is correct (a format-wide restriction shouldn't require a hero to
  detect) and is what makes `FORMAT_RESTRICTION` genuinely reachable/
  testable today despite plan L7 having no concrete IAR-specific rule yet -
  it fires for the *general* banned-list mechanism, not a specific IAR rule.
- `ARENA_CARD_IN_DECK` checks `object_type != "deck"` rather than only
  `is_arena_card`, so a `hero` or `token` object accidentally placed in
  `deck_cards` is caught by the same violation rather than silently passing.
- `hero` must be `object_type == "hero"` when not `None` - raises
  `ValueError` otherwise (same convention as `card_playable_by`, a caller
  bug, not a legality outcome).
- Kept `legal_pool` and `validate_deck` fully decoupled from any
  `*.format.json` loading (that's I/O, forbidden in `packages/core`) -
  callers resolve the drafted pool, all-set-cards list, and hero Card
  themselves and pass plain `Card` lists in.

## VERIFY items resolved or escalated

- Resolved: the weapon/equipment slot constraints flagged as `VERIFY` in
  plan section 2.3 ("must be confirmed against the Comprehensive Rules
  before WP-06 is closed" - actually addressed here in WP-09, since WP-06
  scoped itself to class/talent/Specialization only, deferring pool/deck

## Known limitations

- The CR's finer "Off-Hand" subtype rule (CR 8.2.10a: "cannot be equipped
  with another off-hand equipment") isn't modeled - `Card` doesn't
  currently distinguish an off-hand equipment card from any other 1-handed
  weapon-zone object via a dedicated field. Two off-hands would incorrectly
  validate as legal (2 total hands, no `WEAPON_HANDS` violation) when CR
  8.2.10a says they can't combine regardless of hand count. Flagged, not
  silently worked around - would need a `subtypes`-based check
  (`"Off-Hand" in card.subtypes`, already present in real data) added if
  this ever matters for training realism.
- `FORMAT_RESTRICTION` has no real IAR-specific rule to test against yet
  (plan L7 unpublished) - only the general banned-list mechanism is
  exercised (a synthetic banned uid in tests, mirroring how WP-06 tests its
  own banned-list check).
