# WP-10: Pool and deck metrics + IAR tags

**Status:** DONE
**Date:** 2026-09-14

## What was built

- `packages/core/fabdraft_core/deck/iar_tags.py` (pure, no I/O): `has_blood_debt`,
  `has_go_again`, `is_gate_generator`, `is_banished_zone_payoff`,
  `is_usurp_enabler`, `is_runechant_generator` - keyword/text matchers over
  `Card.functional_text` (and `.keywords` where already populated), plan S12.
  Each has a docstring documenting its known false-positive/false-negative
  risk, grounded against real IAR card text (`data/IAR/cards.json`,
  gitignored, read for research only - never copied into committed files):
  - **Found and avoided a real false-positive trap**: every Basic-rarity
    card legal in this format carries boilerplate reminder text
    ("...in Usurp the Shadow Throne limited formats.") that contains the
    substring "usurp" as part of the *set name*, not the keyword. A naive
    substring search would tag every Basic card as a Usurp enabler.
    `is_usurp_enabler` matches only the bolded keyword form (`**Usurp**`)
    or the verb form (`usurped`), neither of which appears in that
    boilerplate phrase.
  - `is_runechant_generator` distinguishes a card that *creates* a
    Runechant token from one that merely *consumes/references* one (e.g.
    "destroy a Runechant if able") - confirmed both patterns exist in real
    text; only the former is a "generator" per plan S12's own wording.
  - `is_banished_zone_payoff` uses a proximity regex ("play ... from ...
    banished zone") rather than a bare "banished zone" substring search, to
    exclude plain banish-effect cards (e.g. "Banish a card from your
    hand.") that aren't payoffs for the zone itself - documented as an
    imprecise text heuristic, not a semantic classifier.
- `packages/core/fabdraft_core/deck/metrics.py` (pure, no I/O): `hero_playable_counts`
  (reuses `card_playable_by` from WP-06, no duplicated class/talent logic),
  `pitch_distribution`, `cost_curve`, `attack_action_count`/`is_attack_action`,
  `average_power`, `defense_profile` (→ `DefenseProfile`: `defense_3_count`,
  `average_defense`, `blue_block_count`), `go_again_density`,
  `arcane_source_count`, `equipment_coverage_by_slot`, `iar_tag_counts`, and
  an aggregator `compute_pool_shape(cards, heroes=None) -> PoolShape`.

## Decisions taken

- **"Never a rating" enforced by naming, not just intent**: every public
  name in `metrics.py` is a count/distribution/density
  (`attack_action_count`, `pitch_distribution`, ...), never `score`/
  `rating`/`grade`/`rank`. `test_no_metric_field_name_reads_as_a_rating`
  asserts this mechanically over the module's public names, so a future
  addition can't accidentally reintroduce evaluative naming without a test
  failing.
- **`arcane_source_count` is a documented best-effort text proxy**, not a
  structural count: `Card` has no dedicated `arcane` field (the upstream
  the-fab-cube/Card-Vault schemas' arcane-cost concept was never carried
  into our contract during WP-01). Counts any functional-text mention of
  "arcane" - over-counts relative to a true source/resource count. Flagged
  rather than silently treated as precise.
- `equipment_coverage_by_slot` and other metrics operate on whatever
  `cards` list the caller passes (pool or a proposed 30-card deck) rather
  than hard-coding "pool" vs "deck" - matches plan section 6.4's own framing
  ("computed... over `(pool, hero, deck)`") without duplicating each metric
  for both cases.
- `hero_playable_counts` is keyed by hero **uid**, not name, since two
  heroes could in principle share a display name (not observed in IAR, but
  cheap to get right).

## Known limitations

- `arcane_source_count` (see above) is approximate, not structural.
- `is_banished_zone_payoff`'s proximity regex is a heuristic, not a parser
  - documented false-positive/negative surface in its own docstring.
- IAR tag matchers were calibrated against real IAR card text but only
  spot-checked (not exhaustively validated against all 262 real cards) -
  if WP-15/WP-16 (agents) or a future report screen show obviously wrong
  tag counts against real data, recheck these matchers first.
