# WP-11: Log writers

**Status:** DONE
**Date:** 2026-09-14

## What was built

Plan section 7's two remaining logging artefacts (`events.jsonl` already
existed from WP-04's `fabdraft_core.logs.jsonl`):

- **`packages/core/fabdraft_core/logs/markdown.py`**:
  `render_draft_log(events, cards, *, seat_labels=None, casual_mode=False,
  data_integrity="complete", pack_config=None) -> str` + `write_draft_log`.
  Renders the full section 7 narrative from a real event log: session
  header (session id, seed, pod size, casual mode, data integrity, seat
  configuration if given, estimated-pack-weight slot ids from
  `PackConfig`), then per round / per pick: pack size, every offered card
  resolved to name/pitch/rarity/cost/power/defense, the pick made, and a
  `TIMED OUT` marker (+ `reason`) when applicable; review window notes;
  pool-finalized total; and a "Deck build" section.
- **`packages/core/fabdraft_core/logs/session.py`**:
  `build_session_summary(events, *, seat_labels=None) -> dict` +
  `write_session_json`. Real seed/pod-size/timestamps/pick-and-timeout
  counts from the event log; `seat_agents` from the caller; `per_seat_hero`
  / `deck_validity` populated only if `HERO_SELECTED`/`VALIDATION_RESULT`
  events are actually present; `llm_cost_usage` always `{}` today (no LLM
  agent exists, WP-16).
- **Golden-file tests** (`packages/core/tests/test_logs_markdown.py`,
  `test_logs_session.py`): run a real draft via
  `fabdraft_core.draft.engine.run_draft` against the `FIXTURE` set and
  render both artefacts from its actual event log - not hand-built events -
  then assert every documented section is present with real data (all 3
  rounds, pick 1 through 14, real card names/rarities, the 336-total
  pool-finalized line, review window text). Both real-agent-metadata
  branches (reasoning/alternatives; HERO_SELECTED/VALIDATION_RESULT) are
  separately unit-tested with small synthetic events, since nothing in this
  codebase produces them yet (see "Known limitations").

## Interfaces exposed

- `fabdraft_core.logs.markdown.{render_draft_log, write_draft_log}`
- `fabdraft_core.logs.session.{build_session_summary, write_session_json}`

## Decisions taken

- **No deck-build orchestrator was built.** WP-09's `validate_deck` is a
  pure function, not an event emitter - nothing in this codebase currently
  produces `HERO_SELECTED`/`DECK_CARD_ADDED`/`DECK_CARD_REMOVED`/
  `DECK_SUBMITTED`/`VALIDATION_RESULT` events. Building one would have been
  real scope creep (that's WP-18's session-manager territory, most likely).
  Instead, `render_draft_log`'s "Deck build" section renders every one of
  those event types generically *if present* in the given log, and an
  explicit `_Pending: ...` message (not an empty section, not an error)
  when none are - so the artefact is honest about what it does and doesn't
  have data for.
- **`SESSION_CREATED`'s payload was left unchanged** (`{"session_id":
  ...}` only, from WP-07). Seed/pod-size/seat-configuration are read from
  the `SEED_SET`/`POD_SEATED` events (which already carry them) plus an
  explicit `seat_labels` parameter the caller supplies - no need to touch
  `engine.py` for this WP.
- **Model reasoning/alternatives** (plan section 7's "for model seats the
  recorded reasoning and alternatives") are rendered only when a pick
  event's payload actually has `agent`/`decision` keys (matching the shape
  sketched in plan section 5.5's example `PICK_MADE` payload). No event
  emitted by WP-07 today has them - covered by a synthetic-event unit test,
  not the golden draft.
- Kept both renderers pure functions over `(events, cards, ...)` - no
  hidden state, no assumptions about what produced the event list, so
  WP-12 (replay) or WP-18 (live session) can call them identically.

## Known limitations

- **No deck-build events exist to render** until something (most likely
  WP-18's session manager, wrapping WP-09's `validate_deck` +
  hero/arena/deck selections into an event-sourced flow) actually emits
  `HERO_SELECTED`/`DECK_CARD_ADDED`/`DECK_CARD_REMOVED`/`DECK_SUBMITTED`/
  `VALIDATION_RESULT`. Until then, every real `draft_log.md`'s "Deck build"
  section will show the `_Pending` message - this is correct/expected
  behavior given the current architecture, not a bug in this WP.
- **No per-pick timing data.** WP-07's events carry `timed_out` (bool) and
  `reason` (for auto-picks) but not an actual `time_used_ms` per pick - the
  engine advances its simulated clock once per whole pick window (all 8
  seats at once), not per individual seat's response latency. Plan section
  5.5's example payload shows a `time_used_ms` field that doesn't exist in
  any event WP-07 emits today; `render_draft_log` doesn't render it because
  there is nothing to render. If per-seat timing ever matters (e.g. for a
  real human/API-latency `RealClock` session), WP-07's `engine.py` would
  need a small extension to record it - not something to fix in this WP.
- `session.json`'s `llm_cost_usage` is always `{}` - no LLM agent (WP-16)
  exists to produce token/cost data yet.

## What the next WP needs to know

- WP-12 (replay) can use `fabdraft_core.logs.jsonl.read_events` (WP-04) to
  load a log back and pass it straight into `render_draft_log`/
  `build_session_summary` to regenerate identical artefacts - no format
  changes needed for replay compatibility.
- Whoever builds the deck-build event emitter (WP-18, most likely) should
  emit the 5 deck-build event types with plain, JSON-serializable payloads
  (a dict is rendered as-is by `_deck_build_section` today) - once shaped
  data exists, this WP's renderer already knows what to do with it, but its
  exact rendering (currently just `{event.type} (seat X): {payload}`) may
  be worth revisiting for readability once real payloads exist.
